# Правила работы над этим проектом

Здесь только то, что уже было нарушено и стоило времени. Не общие советы,
а память о конкретных ошибках.

---

## Сначала слить к себе из главной ветки

Главное правило, и оно первое по порядку: **прежде чем что-то делать в
своей ветке, влей в неё `main`.** Не в конце, когда пора отдавать работу,
а в начале — и потом ещё раз перед отдачей.

```
git fetch origin main && git merge origin/main
```

**Почему это записано.** Пока шла работа над ветвью с точностью протокола,
`main` ушёл на четыре коммита вперёд, и один из них переписал ровно то
место, которое правилось здесь: поиск пары. Своё сокращение перебора
оказалось выброшено целиком — его сделали заново и лучше, законом
`core/Mating.hpp`. Заодно в `main` исчезло поле настройки
(`max_erosion_depth`), и машинная проверка настроек падала на ветке,
которая этого поля не трогала вовсе.

Обе новости стоили того, что они стоили, только потому, что пришли
последними. Влитая в начале главная ветка сообщила бы их сразу — и работа
не пошла бы туда, где её уже сделали.

## Новый параметр конфигурации обязан проехать весь круг

Круг такой:

```
config.json -> ServerConfig -> RegenerationRequest -> панель клиента
            -> RegenerationRequest -> ServerConfig -> config.json
```

Параметр, потерянный на любом переходе, ведёт себя одинаково скверно и
одинаково незаметно: ползунок двигается, мир не меняется, файл не
меняется, и никто не ругается.

**Добавив параметр, проверь его сохраняемость машинно, а не глазами:**

```
./build.sh && python3 tools/check_config_roundtrip.py
```

Проверка даёт каждому полю своё значение, потом меняет каждое ещё раз и
сверяет файл. Потерянное поле называется по имени. Добавляя параметр,
допиши его в `PROBE` внутри проверки — иначе она его не увидит.

Места, которые правятся вместе (список полей теперь **один**, в
`shared/config/Config.hpp` рядом со структурами):

| Что | Где |
| --- | --- |
| Поле структуры и умолчание | `shared/config/Config.hpp` |
| Список для JSON | `NLOHMANN_DEFINE_TYPE_...` там же |
| Перекладывание в обе стороны | `toRegenerationRequest` / `applyGeneration` там же |
| Перенос в ядро | `toTerrainParams` / `toPlantParams` / `toAnimalParams` в `server/src/main.cpp` |
| Ползунок | `clients/desktop/src/SettingsPanel.cpp` |
| Поле проверки | `PROBE` в `tools/check_config_roundtrip.py` |

**Почему это записано.** Так вышло дважды. Настройки растений — коммит
«Не сохранялись параметры». Потом настройки животных: секция появилась в
конфигурации, в панели и в протоколе, но её забыли дописать в два места,
перекладывающих поля, и поголовье не доезжало НИКУДА — панель показывала
умолчания, мир рождался с умолчаниями, «Save values» молча выбрасывал
правки. Списков полей было три, в разных файлах; кто добавлял секцию,
правил тот из трёх, который вспомнил. Теперь список один, но и его можно
не заметить — потому и есть машинная проверка.

## Не трогай `config.json` пользователя

В нём подобранные вручную значения, а не умолчания. Удалить файл и дать
серверу создать его заново — значит выбросить чужую настройку мира.

Если формат меняется, **переведи каждое значение**, а не сбрасывай. Сверь
перевод по старому файлу из истории (`git show <коммит>:config.json`), поле
за полем.

---

## Проверяй величины, а не только типы и диапазоны

Проверка «все значения целые и в объявленных пределах» проходит полностью
на коде, где величина в тысячу раз не та.

Так и случилось при переводе мира в целые числа: в четырёх местах
величины милли-шкалы перемножались без обратного деления на `kFull`. Туша
давала 8 000 000 биомассы вместо 8000, травоядное съедало куст целиком
каждый тик. Диапазоны сошлись, поведение — нет, и в отчёт попали числа,
измерявшие ошибку.

**Меняя закон мира, сравни поведение с базой:** тот же seed, тот же мир,
ядро до и ядро после, и сличи численность, объём воды, минералы. Ожидание
— не совпадение (изменения намеренные), а **тот же порядок величин**.
Расхождение в разы — повод разбираться, а не строчка в отчёте.

---

## Дробные величины в состоянии мира

Их нет и быть не должно — см. `core/include/core/Scale.hpp`. Дробь всегда
тянет за собой поле-накопитель, в котором она дожидается целого.

Скорость, которая целой не выходит, выражается **сроком** («одна крупица
раз в N тиков») или **разностью двух делений** (величина от номера тика
или возраста). Срок не описывает ничего быстрее единицы за тик — если
настройку приходится крутить быстрее, нужна разность делений.

## Новое поле животного тоже обязано проехать круг

Круг у него свой, но ловушка та же, что у настроек:

```
компонент -> карточка животного (world_init) -> дельта -> клиент
```

Карточка уходит один раз, при рождении. Поле, которое меняется за жизнь, а
в дельту его дописать забыли, замрёт на том значении, с которым животное
родилось, — и увидеть это будет нечем: зверь на карте выглядит зверем,
просто чуть-чуть не тем.

**Добавив поле, реши, меняется ли оно за жизнь.** Не меняется (вид, диета,
пол) — только карточка. Меняется — карточка И дельта:

| Что | Где |
| --- | --- |
| Поле снимка | `LayerSnapshot::AnimalView` в `server/NetworkServer.hpp` |
| Заполнение | `captureLayers` там же |
| Карточка | `animalToJson` в `server/NetworkServer.cpp` |
| Дельта (только меняющееся) | `animalsDeltaJson` там же |
| Разбор карточки | `parseAnimal` в `clients/desktop/src/NetworkClient.cpp` |
| Разбор дельты | `applyAnimalChanges` там же |

Проверка машинная, глазами тут не поймать ничего:

```
./build.sh && python3 tools/check_animal_delta.py
```

Она собирает список ровно так, как это делает клиент, и сличает с полным
`world_init`, остановив мир. Сличать на разных тиках бессмысленно —
разойдётся не дельта, а время.

---

## Комментарии объясняют «почему», а не «что»

Так написан весь проект. Комментарий, пересказывающий код, здесь лишний;
комментарий, объясняющий, почему выбрано это, а не очевидное другое, и что
сломалось при очевидном другом, — обязателен. Сноси комментарий вместе с
кодом, который он объяснял, и пиши новый, если причина изменилась.
