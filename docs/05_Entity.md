# Entity / Component / System(Goblins)

## Назначение документа

Данный документ описывает базовую архитектурную модель ECS: что такое Entity, Component и System, как они хранятся и как взаимодействуют между собой.

Документ опирается на принципы, описанные в 02_CorePrinciples.md, и не должен им противоречить.

---

# Фундаментальные положения

- Entity — это только идентификатор, не содержащий данных.
- Component — это только данные, не содержащие логики.
- System — это единственное место, где выполняется логика.
- Системы не хранят состояние между тиками.
- Системы не вызывают друг друга напрямую.
- Создание и удаление Entity происходит через очередь команд.

---

# 1. Entity

Entity — это число (идентификатор).

- Entity не хранит данные.
- Entity не хранит тип, тег или какую-либо иную информацию.
- Наличие или отсутствие возможностей у Entity определяется исключительно набором компонентов, привязанных к этому идентификатору.

Это напрямую следует из принципа "Всё является Entity" и "Поведение определяется компонентами" (02_CorePrinciples).

---

# 2. Component

Component — это данные, привязанные к конкретному Entity.

- Компонент не содержит методов и логики.
- Компонент не содержит валидации.
- Компонент — это структура полей одного типа (например: PositionComponent, HealthComponent).
- У Entity может быть не более одного экземпляра компонента каждого типа.
- Наличие компонента у Entity означает наличие соответствующей возможности. Отсутствие компонента означает отсутствие возможности.

---

# 3. System

System — это то, что выполняет вычисление следующего состояния мира.

- Система запрашивает (query) все Entity, обладающие определённым набором компонентов.
- Система изменяет данные этих компонентов за один тик.
- Система не хранит собственное состояние между тиками — любое состояние, влияющее на результат, должно находиться в компонентах Entity.
- Система не знает о существовании других систем.

Один тик — это последовательное выполнение всех систем в фиксированном порядке (см. 04_WorldModel, п.8).

---

# 4. Хранение Entity и Component

Данные хранятся по типам компонентов, а не по Entity.

- Для каждого типа компонента существует отдельное хранилище (например: хранилище всех PositionComponent, хранилище всех HealthComponent).
- Entity — это идентификатор, по которому можно получить компонент нужного типа из соответствующего хранилища, если он там есть.
- Query системы — это выборка Entity, для которых одновременно существуют записи во всех запрошенных хранилищах компонентов.

Такое хранение выбрано сразу, а не как будущая оптимизация, так как является типичным и естественным способом организации данных для ECS.

---

# 5. Создание и удаление Entity

Создание и удаление Entity, а также добавление и удаление компонентов, не происходит мгновенно в момент вызова.

- Изменения записываются в очередь команд.
- Очередь команд разрешается между тиками, после завершения работы всех систем текущего тика.
- Это предотвращает изменение коллекций Entity/Component во время их обработки системами внутри одного тика.

---

# 6. Взаимодействие систем

Системы не вызывают друг друга напрямую.

Единственный способ взаимодействия систем — изменение состояния компонентов.

- Система A не может вызвать функцию системы B.
- Система A может изменить компонент, который затем будет прочитан системой B на этом же или следующем тике.

Это жёсткое правило архитектуры. Оно обеспечивает:

- независимость систем друг от друга;
- возможность добавлять, убирать или заменять системы, не затрагивая остальные;
- возникновение сложного поведения из простых правил (принцип 14, 02_CorePrinciples), поскольку взаимодействие систем возможно только через объективное состояние мира, а не через прямые команды.
