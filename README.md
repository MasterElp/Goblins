World simulator
# Главная идея
- Проект представляет собой автономную симуляцию живого мира.
- Основой проекта является не игровой процесс, а моделирование мира, который способен существовать, развиваться и изменяться независимо от присутствия игрока.
- Игрок не является центром мира. Он лишь один из возможных наблюдателей или участников происходящих событий.

# Goblins

Симуляция мира. Архитектура и философия проекта — в `docs/`.

## Быстрый старт

Windows:
```
build.bat
run.bat
```

Linux/macOS:
```
./build.sh
./run.sh
```

`build.*` собирает и server, и client. `run.*` поднимает сервер в фоне
(на Windows — в отдельном окне консоли), ждёт, пока он займёт порт,
запускает клиента (открывается окно) и сам останавливает сервер по
завершении клиента (или по Ctrl+C).

На Windows — именно `.bat`, не PowerShell-скрипты: `.bat` не требует
менять политику выполнения скриптов, ничего дополнительно разрешать не
нужно, просто двойной клик или запуск из `cmd`.

## Клиент — графическое приложение

После запуска показывает главное меню с тремя пунктами: **Settings**,
**World Generation**, **Simulation**. `Esc` — назад в меню из любого
экрана. Окно можно свободно менять в размерах (resizable).

**Simulation** ведёт не сразу в мир, а на экран выбора мира: симулируется
всегда конкретный сохранённый мир (см. "Select world" ниже).

### Settings

Разрешение (фиксированные пресеты — 1280x720 / 1600x900 / 1920x1080 /
2560x1440) и переключатель полноэкранного режима (настоящий exclusive
fullscreen, не безрамочное окно). Изменения применяются сразу и
сохраняются в `config.json` — не нужно отдельной кнопки "Сохранить".

### World Generation — этап 1: почва и вода

Вся карта всегда видна целиком, без прокрутки: размер тайла
пересчитывается каждый кадр под текущий размер окна, поэтому при его
изменении меняется только масштаб отображения, а не то, сколько карты
видно (в отличие от Simulation, см. ниже). Тайл под курсором
подсвечивается, его параметры почвы показаны внизу экрана.

Справа — панель настроек генерации: все параметры из `terrain` (см.
ниже) в виде ползунков, плюс seed'ы (со случайной перегенерацией по
кнопке "Random") и число булыжников. При подключении панель сама
заполняется текущими параметрами сервера — так видно, чем именно
сгенерирован мир на экране.

Кнопка **Regenerate** отправляет серверу
`{"type": "regenerate", "params": {...}}`. Сервер — единственный источник
истины: он удаляет прежние Entity почвы/воды/булыжников, генерирует
заново на том же месте (размер Области не меняется — для этого нужен
перезапуск с новым `area` в конфигурации) и рассылает свежий снапшот
**всем** подключённым клиентам, не только тому, кто нажал кнопку.
Регенерация выполняется на потоке игрового цикла между тиками, не
прерывая его: тик просто продолжается со следующего номера.

Кнопка **Reset to current server state** отбрасывает несохранённые правки
и возвращает ползунки к текущему состоянию сервера.

Кнопка **Save as world** (сверху, слева от "Back") сохраняет то, что
сейчас на экране, как отдельный мир — он появится в списке на экране
выбора мира. Только что сгенерированный мир всегда стоит на нулевом
тике, поэтому в списке он окажется ровно в том состоянии, в каком его
видно здесь. Сама по себе регенерация ничего на диск не пишет: пока не
нажата эта кнопка, мир существует только в памяти сервера.

Следующие этапы генерации (растительность, экосистема, животные — см.
02_CorePrinciples.md, п.5) сюда добавятся позже; сейчас реализован только
первый.

### Select world — выбор мира перед симуляцией

Пункт **Simulation** в меню открывает список сохранённых на сервере
миров: имя, номер тика, размер Области, seed террейна и время последнего
сохранения. Клик по строке загружает этот мир и запускает симуляцию с
того тика, на котором он был сохранён; мир на нулевом тике так и
помечен — он ещё ни разу не тикал, это состояние сразу после генерации.
Текущий загруженный мир выделен цветом.

Кнопка **New world** генерирует новый мир текущими параметрами генерации
(теми, что на экране World Generation) — сервер сразу сохраняет его как
мир с нулевым тиком и запускает симуляцию.

Если сохранённых миров нет вообще, выбирать не из чего: экран сам
запрашивает генерацию нового мира и уходит в симуляцию. Именно поэтому
клиент различает "миров нет" и "список ещё не пришёл" — по второму мир не
создаётся, иначе каждый запуск клиента плодил бы лишние миры.

### Simulation

Прокручиваемый вид мира с фиксированным размером тайла (`tile_size` из
конфигурации) — при изменении размера окна меняется не масштаб, а
сколько тайлов видно одновременно. Тайл под курсором подсвечивается,
каждый тайл окрашен смешением почвенных параметров (каменистость и
утрамбованность задают материал, влажность затемняет поверх), вода —
отдельным сине-бирюзовым оттенком, темнее с глубиной; булыжники —
маленькие тёмные квадраты поверх почвы.

В верхней полосе — имя текущего мира и номер тика, кнопка **Save world**
(сохраняет полное состояние мира на текущем тике поверх того же файла, из
которого мир загружен) и **Back (Esc)**. Сохранение не останавливает мир:
сервер записывает его между тиками.

Управление:
- `W`/`A`/`S`/`D` или стрелки — плавная прокрутка.
- `P` — пауза/возобновление мира. Это не локальная заморозка картинки, а
  настоящая команда серверу: пока мир на паузе, `GameLoop` не выполняет
  тиков вообще, и это видят все подключённые клиенты одновременно (в углу
  экрана появляется отметка `PAUSED`).

## Конфигурация

Конфигурации сервера и клиента **разделены** — каждая живёт рядом со
своим исполняемым файлом, а не в одном общем файле.

### Сервер — `config.json` в корне репозитория

```json
{
    "host": "127.0.0.1",
    "port": 9002,
    "area": { "width": 100, "height": 100 },
    "terrain_seed": 54321,
    "terrain": { "...": "см. ниже" },
    "boulder_count": 40,
    "boulder_seed": 12345,
    "tick_interval_ms": 200,
    "tick_count": -1,
    "saves_dir": "saves"
}
```

- `host`, `port` — где сервер слушает WebSocket.
- `area` — размер Области в тайлах (04_WorldModel.md, п.2).
- `terrain_seed` — seed для генерации почвы/рек/прудов; один и тот же seed даёт один и тот же результат.
- `terrain` — все числовые параметры генерации почвы и водоёмов, подробности ниже.
- `boulder_count`, `boulder_seed` — сколько непроходимых булыжников и с каким seed их генерировать (04_WorldModel.md, п.4); один и тот же seed даёт одну и ту же карту.
- `tick_interval_ms` — целевой интервал тика (06_GameLoop.md, п.4).
- `tick_count` — сколько тиков выполнить; `-1` — бесконечно (мир существует независимо от наблюдателя, 02_CorePrinciples.md, п.1).
- `saves_dir` — каталог сохранённых миров (по одному JSON-файлу на мир). Относительный путь — относительно каталога исполняемого файла сервера, не рабочей директории; абсолютный используется как есть. Каталог создаётся при первом сохранении.

Отсутствующие в файле поля берут значения по умолчанию — старый
`config.json` без новых полей остаётся рабочим, а не считается
невалидным целиком.

#### `terrain` — параметры генерации почвы и водоёмов

Метод (реализация — `core/src/generation/TerrainGenerator.cpp`): heightmap
на фрактальном шуме (fBm, OpenSimplex2) → реки как явные русла (у каждой
один случайный исток и один случайный конец на разных сторонах карты;
путь идёт курсом на цель с боковым отклонением от шума и лёгким
притяжением к более низкому рельефу — оба подавляются собственной
случайной скоростью реки, чем быстрее река, тем прямее; ширина и глубина
"дышат" вдоль пути через отдельный шум; река, упёршаяся в уже принятую,
либо сливается с ней и делает её шире ниже по течению, либо путь целиком
переигрывается — так русла разных рек не наезжают друг на друга нигде,
кроме точек слияния) — русло вырезается в heightmap ДО заливки впадин →
Priority-Flood (Barnes et al., 2014) для заполнения впадин (пруды,
естественно образующиеся в том числе поверх/вдоль уже вырезанного русла)
→ влажность через distance transform от воды. Ни одно число не зашито в
код — всё ниже читается из конфигурации.

```json
{
    "height_noise_frequency": 0.02,
    "rock_noise_frequency": 0.05,
    "compaction_noise_frequency": 0.04,
    "moisture_noise_frequency": 0.03,
    "noise_octaves": 4,
    "noise_lacunarity": 2.0,
    "noise_gain": 0.5,
    "rock_height_bump": 0.35,
    "compaction_height_bump": 0.25,
    "river_count": 3,
    "river_width": 3.0,
    "river_sinuosity": 0.5,
    "river_depth": 1.5,
    "river_max_flow_speed": 1.0,
    "min_pond_depth": 0.01,
    "min_pond_size": 1,
    "max_pond_size": 0,
    "pond_depth_scale": 4.0,
    "moisture_falloff": 8.0,
    "water_moisture_boost": 0.7,
    "rock_moisture_reduction": 0.3,
    "minerals_noise_frequency": 0.06,
    "minerals_average": 10.0,
    "river_minerals": 10,
    "mineral_moisture_threshold": 0.5
}
```

- `*_noise_frequency` — частота fBm-шума для каждого слоя (меньше — крупнее пятна/формы, больше — мельче и чаще).
- `noise_octaves`/`noise_lacunarity`/`noise_gain` — параметры фрактального шума, общие для всех слоёв.
- `rock_height_bump`, `compaction_height_bump` — насколько каменистость/утрамбованность поднимают высоту рельефа (вода физически огибает такие участки — этим и обеспечивается требование "где утрамбовано и каменисто, реки быть не может", без ручных исключений).
- `river_count` — сколько рек генерировать; каждая — явное русло (не эмерджентный порог) со своим случайным истоком и концом на разных сторонах карты. Русла разных рек не пересекаются друг с другом — либо явно сливаются (становясь шире), либо путь целиком переигрывается.
- `river_width`/`river_depth` — базовая ширина (тайлы) и глубина русла; оба чуть "дышат" вдоль пути за счёт встроенного шума (не параметр — не настраивается отдельно).
- `river_sinuosity` — базовая извилистость (0 — прямая линия, 1 — максимальный меандр; путь также слегка притягивается к более низкому рельефу). У каждой реки своя случайная скорость потока (см. `river_max_flow_speed`) подавляет и то, и другое — чем быстрее река, тем она прямее.
- `river_max_flow_speed` — верхняя граница скорости потока; у каждой реки при генерации своя случайная скорость до этого предела (у пруда скорость всегда 0 — см. `WaterComponent.flowSpeed`).
- `min_pond_depth` — минимальная глубина впадины, чтобы считаться прудом.
- `min_pond_size`/`max_pond_size` — допустимый размер связной области пруда в тайлах; `max_pond_size: 0` — без верхнего ограничения.
- `pond_depth_scale` — множитель глубины пруда (глубина впадины × этот коэффициент).
- `moisture_falloff` — за сколько тайлов влияние воды на влажность спадает примерно вдвое.
- `water_moisture_boost` — насколько вода поднимает влажность рядом с собой.
- `rock_moisture_reduction` — насколько каменистая почва хуже держит влагу.
- `minerals_noise_frequency` — частота шума минералов (как и другие `*_noise_frequency`).
- `minerals_average` — среднее количество минералов (`SoilComponent.minerals`) на обычной почве; конкретное значение тайла — шум, в среднем сходящийся к этому числу.
- `river_minerals` — минералы на клетках реки: не шум, а всегда это одно и то же значение.
- `mineral_moisture_threshold` — порог влажности для переноса минералов (см. ниже). Это свойство мира, а не параметр текущей симуляции: выбирается здесь, при генерации, записывается на World Entity (`WorldPropertiesComponent`) и во время самой симуляции не меняется — см. docs/06_GameLoop.md, п.1a.

#### Гидрология: почва и вода меняются во время симуляции

В отличие от `terrain` (разовая генерация), `HydrologySystem`
(`core/src/systems/HydrologySystem.cpp`) выполняется **каждый тик**,
сразу после `TimeSystem`:

- Влажность почвы (`SoilComponent.moisture`) медленно движется к
  равновесию, зависящему от расстояния до ближайшей воды: рядом с водой
  растёт, вдали от неё — постепенно высыхает (падает к нулю).
- Утрамбованность (`SoilComponent.compaction`) рядом с водой постепенно
  размягчается — необратимо: если водоём уйдёт, участок останется мягким
  (без причины со стороны воды утрамбованность не меняется).
- Вода течёт по рельефу (`HeightComponent.height` — персистентная высота
  тайла, сохраняемая при генерации из heightmap): каждый тик небольшая
  часть глубины перетекает от более высокой точки поверхности (высота +
  глубина воды) к соседней более низкой, с сопутствующей эрозией — исток
  теряет высоту, приёмник получает ровно столько же. Мягкая и не каменистая
  почва эродирует быстрее, поэтому размягчение усиливает эрозию, а та —
  сдвигает русло/берег, из-за чего очертания рек и прудов постепенно
  меняются. Тайл получает или теряет `WaterComponent`, когда глубина
  пересекает порог появления/исчезания (с гистерезисом, чтобы не мерцало
  на границе).
- Минералы (`SoilComponent.minerals`, целое число) двигаются между
  соседними тайлами: каждый тик тайл A ищет среди соседей, которые
  "притягивают" минералы (есть вода или влажность выше порога
  `mineral_moisture_threshold`), самого бедного минералами B; если A
  богаче B минимум на 2, к B уходит ровно половина разницы (целочисленно)
  — 8 и 6 становятся 7 и 7, 10 и 6 — 8 и 8. Ровно один сосед за тик, не
  несколько: если считать перетоки к нескольким соседям одновременно по
  одному и тому же снимку, тайл может отдать больше, чем у него есть, и
  вместо предсказуемого сглаживания получаются на вид хаотичные "волны".
  Порог — свойство мира (см. выше), а не константа `HydrologySystem.cpp`:
  меняется генерацией/загрузкой другого мира, но не живьём во время
  симуляции.

Скорости этих процессов (кроме самого порога влажности — см. выше) —
внутренние константы в `HydrologySystem.cpp` (не параметры конфигурации,
как и часть механики генерации рек) — подобраны так, чтобы изменения были
заметны за десятки-сотни тиков, а не мгновенно.

### Клиент — `config.json` рядом с `client`/`client.exe`

Клиент **сам создаёт** этот файл при первом запуске, если его нет —
ничего настраивать заранее не нужно:

```json
{
    "host": "127.0.0.1",
    "port": 9002,
    "view": { "width": 60, "height": 25 },
    "scroll_step": 5,
    "tile_size": 16,
    "window_width": 1280,
    "window_height": 720,
    "fullscreen": false
}
```

- `host`, `port` — куда подключаться (адрес сервера).
- `view` — сколько тайлов видно в окне просмотра экрана Simulation (ширина x высота).
- `scroll_step` — скорость прокрутки на экране Simulation, тайлов в секунду при зажатой клавише.
- `tile_size` — размер тайла на экране Simulation, в пикселях. На экране World Generation не используется — там размер тайла всегда подбирается так, чтобы вся карта помещалась в окно.
- `window_width`, `window_height`, `fullscreen` — экран Settings; сохраняются автоматически при изменении.

И сервер, и клиент принимают путь к своей конфигурации первым аргументом
(`server other_config.json`, `client other_config.json`) — если аргумент
не передан, используется `config.json` рядом с самим исполняемым файлом
(создаётся автоматически, если отсутствует). `run.sh`/`run.bat` передают
серверу путь до корневого `config.json`, а клиента запускают без
аргумента — он найдёт/создаст свой сам.

## Зависимости

EnTT, nlohmann/json, IXWebSocket и raylib (только для клиента) лежат
прямо в репозитории — `third_party/` в корне. Ни один CMake-проект в
этом репозитории (ни `server`, ни `clients/desktop`) не обращается к
сети при конфигурации или сборке. `third_party/CMakeLists.txt` —
единственное место, где описано, как их собирать; и корневой
`CMakeLists.txt` (для core/server), и `clients/desktop/CMakeLists.txt`
подключают именно его через `add_subdirectory`, чтобы код и описание
сборки библиотек не повторялись в двух местах. raylib собирается только
для клиента (сервер остаётся headless, без графики/X11/OpenGL) — это
регулируется опцией `GOBLINS_WITH_RAYLIB`, которую включает только
`clients/desktop/CMakeLists.txt`. Так же устроен `shared/` — общий код
(чтение конфигурации, определение пути к своему исполняемому файлу),
который использует и сервер, и клиент.

Системных зависимостей (OpenSSL, zlib, Qt) не требуется — TLS и сжатие
WebSocket-сообщений отключены за ненадобностью на этом этапе (всё
рассчитано на локальную сеть); аудио-модуль raylib отключён (звук в
проекте не используется). На Linux для сборки клиента нужны стандартные
dev-пакеты X11/OpenGL (libx11-dev, libxrandr-dev, libxinerama-dev,
libxcursor-dev, libxi-dev, libgl1-mesa-dev) — на Windows ничего
дополнительно ставить не нужно, всё уже есть в системе.

```
./server/server [путь до config.json]
```

По умолчанию ищет (и создаёт, если нет) `config.json` рядом с собой.
Программа поднимает WebSocket-сервер и ждёт: мир при старте не
генерируется и игровой цикл стоит на паузе, пока клиент не пришлёт
`start_simulation` (создать новый мир или загрузить сохранённый). Дальше
сервер тикает и после каждого тика рассылает подключённым клиентам
свежий полный снапшот мира — `HydrologySystem` меняет почву и воду
непрерывно, поэтому клиенту нужно видеть не только номер тика, а всё
состояние. Весь консольный вывод — на английском (чтобы не зависеть от
кодировки консоли).

### Протокол (WebSocket, JSON)

Сервер → клиент, сразу при подключении, после каждой регенерации и после
КАЖДОГО тика (не только номер — `HydrologySystem` постоянно меняет
почву/воду):
```json
{"type": "world_snapshot", "area": {"width": 100, "height": 100}, "tick": 0,
 "paused": false, "world": "world-20260812-200716",
 "terrain_seed": 54321, "terrain": { "...": "все поля из config.json/terrain" },
 "boulder_count": 40, "boulder_seed": 12345,
 "boulders": [{"x": 12, "y": 34}, ...],
 "soil": {
   "moisture": [0.42, 0.51, "...по одному float на тайл, row-major..."],
   "rockiness": [...],
   "compaction": [...],
   "minerals": [10, 8, "...по одному int на тайл, row-major..."]
 },
 "water": [{"x": 30, "y": 12, "depth": 1.4}, "...только тайлы с водой..."]}
```

Поле `world` — имя мира, который сейчас в памяти сервера; пустая строка
означает, что этот мир ещё не сохранён (например, только что
перегенерирован на экране World Generation).

Сервер → клиент, сразу при подключении и после каждого сохранения мира:
```json
{"type": "world_list", "current": "world-20260812-200716",
 "worlds": [{"name": "world-20260812-200716", "tick": 30,
             "area_width": 100, "area_height": 100,
             "terrain_seed": 54321, "boulder_seed": 12345,
             "created_at": "2026-08-12T20:07:16Z",
             "saved_at": "2026-08-12T20:09:02Z"}, "...свежие сверху..."]}
```

Сервер → клиент, результат операции без собственного ответа (сохранение
и загрузка мира) — клиенту нужно показать, что произошло, особенно при
ошибке:
```json
{"type": "notice", "level": "info", "text": "World saved as '...' (tick 30)."}
```

Сервер → все клиенты, при изменении паузы:
```json
{"type": "pause_state", "paused": true}
```

Клиент → сервер, запрос переключить паузу (в графическом клиенте — по
клавише `P`):
```json
{"type": "toggle_pause"}
```

Клиент → сервер, запрос перегенерировать мир (панель настроек, кнопка
Regenerate) — `params` имеет ту же форму, что `terrain_seed`/`terrain`/
`boulder_count`/`boulder_seed` в `world_snapshot`:
```json
{"type": "regenerate", "params": {"terrain_seed": 777, "terrain": {...},
 "boulder_count": 40, "boulder_seed": 12345}}
```
Сервер полностью сбрасывает мир (все прежние Entity, номер тика — в 0),
генерирует его заново размером Области из конфигурации и рассылает свежий
`world_snapshot` всем подключённым клиентам. Перегенерированный мир
считается новым и безымянным: он никак не связан с файлом, из которого
мир мог быть загружен, пока его явно не сохранят.

Клиент → сервер, запросить список сохранённых миров (ответ —
`world_list`):
```json
{"type": "list_worlds"}
```

Клиент → сервер, сохранить полное состояние мира (кнопки "Save world" и
"Save as world"). Пустое `name` — под именем текущего мира, а если мир
ещё не сохранялся, сервер придумает новое:
```json
{"type": "save_world", "name": ""}
```

Клиент → сервер, запустить симуляцию. С именем мира — загрузить
сохранённый мир (его размер Области может отличаться от `area` в
конфигурации); без имени — сгенерировать новый мир текущими параметрами и
сразу сохранить его как мир с нулевым тиком:
```json
{"type": "start_simulation", "world": "world-20260812-200716"}
```

Имя мира — имя файла сохранения без расширения; сервер проверяет его
(только буквы/цифры/`-`/`_`/`.`/пробел) и отвергает всё, что могло бы
увести за пределы каталога сохранений.

Сохранение и загрузка мира, как и генерация, выполняются на потоке
`GameLoop` между тиками: запись читает весь ECS registry, а загрузка его
перезаписывает — делать это параллельно с выполняющимся тиком нельзя.

Пауза настоящая, а не косметическая: пока мир на паузе, `GameLoop` не
выполняет ни одной системы и не рассылает тики — это распространяется на
всех подключённых клиентов одновременно (07_TechStack.md, все
взаимодействия — через интерфейсы, единый источник истины о состоянии
паузы — на сервере).

### Сохранённые миры

Один мир — один файл `<имя>.json` в каталоге `saves_dir` (см.
конфигурацию). Имя файла без расширения и есть идентификатор мира: список
миров не зависит от содержимого файлов, а два мира не могут случайно
оказаться с одним именем. Реализация — `server/src/WorldSave.cpp`; в
`core` этого кода нет, потому что ядро не знает ни о файлах, ни о JSON
(07_TechStack.md, п.6).

Сохраняется **полное состояние мира** — все Entity со всеми компонентами
(включая World Entity с номером тика), а не только seed генерации: мир
после N тиков повторной генерацией уже не восстанавливается. Индекс
размещения по тайлам (`Area`) в файл не пишется — он выводится из
`PositionComponent`/`ImpassableComponent` и перестраивается при загрузке.

```json
{"format": "goblins_world", "version": 1,
 "info": {"name": "...", "tick": 0, "area_width": 100, "area_height": 100,
          "terrain_seed": 54321, "boulder_seed": 12345,
          "created_at": "...", "saved_at": "..."},
 "generation": {"terrain_seed": 54321, "terrain": {...},
                "boulder_count": 40, "boulder_seed": 12345},
 "entities": [{"position": {"x": 0, "y": 0},
               "soil": {"moisture": 0.42, "rockiness": 0.1, "compaction": 0.3},
               "height": 0.57,
               "water": {"depth": 1.4, "flow_speed": 0.7}},
              {"position": {"x": 12, "y": 34}, "impassable": true},
              {"time": {"tick": 0}}]}
```

`height` (`HeightComponent`) добавлено без смены версии формата — старые
файлы без этого поля читаются как есть (высота считается плоской, 0).

Мир сохраняется сразу после генерации — с нулевым тиком, то есть ровно в
том состоянии, в каком он появился на свет, ещё до первого тика. Дальше
его можно сохранять сколько угодно раз кнопкой "Save world": запись идёт
поверх того же файла (`created_at` при этом сохраняется, `saved_at` и
`tick` обновляются), а сама запись атомарная — через временный файл с
переименованием, чтобы прерванное сохранение не портило предыдущую
версию мира.

## Десктопный клиент

Отдельный CMake-проект в `clients/desktop` — собирается независимо от
сервера (свой `add_subdirectory` на общие `third_party/` и `shared/`, см.
выше). Графическое приложение на raylib.

### Сборка

```
cd clients/desktop
mkdir build && cd build
cmake ..
cmake --build . -j
```

### Запуск

Сначала должен быть запущен сервер. Затем:

```
./client [путь до config.json]
```

По умолчанию ищет (и создаёт, если нет) `config.json` рядом с собой и
подключается к `host:port` из него.

## Структура

- `config.json` — конфигурация сервера (у клиента своя, рядом с его бинарником).
- `third_party/` — vendored-зависимости (EnTT, nlohmann/json, IXWebSocket, raylib), общие для core/server и клиента.
- `shared/` — общий код (конфигурация, путь к исполняемому файлу, описание сохранённого мира в протоколе), общий для server и client.
- `core/` — ядро симуляции: ECS (EnTT), компоненты, системы, игровой цикл, генерация мира. Не зависит от server/clients.
- `server/` — исполняемый файл `server`, оборачивающий core: игровой цикл, WebSocket-слой (IXWebSocket + nlohmann/json) и сохранение/загрузка миров (`WorldSave`).
- `clients/desktop/` — исполняемый файл `client`, графическое приложение на raylib. Получает данные только по WebSocket-протоколу сервера.
- `clients/web/` — будущий браузерный клиент.
- `docs/` — архитектурные документы проекта.
- `build.sh`/`run.sh` (Linux/macOS) и `build.bat`/`run.bat` (Windows) — сборка и запуск сервера+клиента одной командой.
