World simulator
# Главная идея
- Проект представляет собой автономную симуляцию живого мира.
- Основой проекта является не игровой процесс, а моделирование мира, который способен существовать, развиваться и изменяться независимо от присутствия игрока.
- Игрок не является центром мира. Он лишь один из возможных наблюдателей или участников происходящих событий.

# Goblins

Симуляция мира. Архитектура и философия проекта — в `docs/`.

## Быстрый старт

```
./build.sh
./run.sh
```

`build.sh` собирает и server, и client (весь вывод дублируется в
`build.log`). `run.sh` поднимает сервер в фоне, ждёт, пока он займёт порт,
запускает клиента (открывается окно) и сам останавливает сервер по
завершении клиента (или по Ctrl+C).

На Windows — те же скрипты из Git Bash или WSL (бинарники с `.exe` они
находят сами). Отдельных `.bat` больше нет. Можно и просто собрать
проекты обычным CMake — как описано ниже, отдельно сервер и отдельно
клиент.

## Клиент — графическое приложение

После запуска показывает главное меню с двумя пунктами: **Settings** и
**World**. `Esc` — назад в меню из любого экрана. Окно можно свободно
менять в размерах (resizable).

### Settings

Разрешение (фиксированные пресеты — 1280x720 / 1600x900 / 1920x1080 /
2560x1440) и переключатель полноэкранного режима (настоящий exclusive
fullscreen, не безрамочное окно). Изменения применяются сразу и
сохраняются в `config.json` — не нужно отдельной кнопки "Сохранить".

### Select world — выбор мира

**World** ведёт не сразу в мир, а на список сохранённых на сервере миров:
имя, номер тика, размер Области, seed и время последнего сохранения. Клик
по строке загружает мир и продолжает его с того тика, на котором он был
сохранён; мир на нулевом тике так и помечен — он ещё ни разу не тикал, это
состояние сразу после генерации. Текущий загруженный мир выделен цветом.
Кнопка **Delete** в строке удаляет мир (с подтверждением).

Кнопка **New world** генерирует новый мир текущими параметрами генерации
(теми, что на панели параметров экрана мира). На диск он при этом не
пишется — пока не нажата "Save world", мир существует только в памяти
сервера.

Если сохранённых миров нет вообще, выбирать не из чего: экран сам
запрашивает генерацию нового мира и открывает его. Именно поэтому клиент
различает "миров нет" и "список ещё не пришёл" — по второму мир не
создаётся, иначе каждый запуск клиента плодил бы лишние миры.

### World — один экран на генерацию и на наблюдение

Экран мира один: и подбор параметров генерации, и наблюдение за
симуляцией — это один и тот же мир на одной и той же карте. Раньше их было
два, и они отличались только тем, крутится ли рядом панель настроек; за
это приходилось дублировать отрисовку карты и подсказку по тайлу, а при
переключении терялись прокрутка, масштаб и включённые слои.

Прокручиваемый вид с масштабированием. Тайл под курсором подсвечивается,
его параметры почвы, трава на нём и перегной показаны внизу экрана. Каждый
тайл окрашен смешением почвенных параметров (каменистость и
утрамбованность задают материал, влажность затемняет поверх), вода —
отдельным сине-бирюзовым оттенком, темнее с глубиной; булыжники —
маленькие тёмные квадраты поверх почвы. Трава подмешивает к цвету тайла
цвет своего вида — тем сильнее, чем крупнее выросло растение; перегной на
месте умершей травы — тёмное пятно.

В верхней полосе — имя текущего мира и номер тика, кнопки **Save world**
(спрашивает имя; по умолчанию — имя текущего мира, то есть запись поверх
того же файла), **Params (G)**, **Stop/Start** (пауза) и **Back (Esc)**.
Сохранение не останавливает мир: сервер записывает его между тиками.

Управление:
- `W`/`A`/`S`/`D` или стрелки — плавная прокрутка.
- Колёсико мыши — масштаб (к точке под курсором).
- `F` — вписать всю карту в окно.
- `1`–`6` — слои: каменистость, утрамбованность, влажность вместе с
  водой, минералы, рельеф, трава вместе с перегноем. Выключенный слой
  просто не участвует в цвете тайла. Под полосой слоёв — легенда видов
  травы: цвет вида и сколько клеток он занимает прямо сейчас (считается по
  тому же снимку, что и рисуется, поэтому видно, как виды делят мир по
  ходу симуляции).
- `G` — панель параметров генерации справа: все параметры из `terrain` и
  `plants` (см. ниже) в виде ползунков, плюс seed (со случайной
  перегенерацией по кнопке "Random") и число булыжников. При подключении
  панель сама заполняется текущими параметрами сервера — так видно, чем
  именно сгенерирован мир на экране. Кнопка **Regenerate** пересоздаёт мир
  этими параметрами, **Save values** — записывает их в `config.json`
  сервера, чтобы они стали умолчанием при следующем запуске.
- `C` — оверлей констант законов мира (только чтение, см. ниже).
- `P` — пауза/возобновление мира. Это не локальная заморозка картинки, а
  настоящая команда серверу: пока мир на паузе, `GameLoop` не выполняет
  тиков вообще, и это видят все подключённые клиенты одновременно.

Регенерация: сервер — единственный источник истины. Он удаляет прежние
Entity, генерирует мир заново на том же месте (размер Области не меняется
— для этого нужен перезапуск с новым `area` в конфигурации) и рассылает
свежее состояние **всем** подключённым клиентам, не только тому, кто нажал
кнопку. Выполняется это на потоке игрового цикла между тиками. Мир после
регенерации считается новым и безымянным: он не связан с файлом, из
которого мог быть загружен, пока его явно не сохранят.

Реализованы первые три этапа генерации (02_CorePrinciples.md, п.5):
карта, природные ресурсы и заселение растительностью. Следующие
(экосистема, животные) добавятся позже.

## Конфигурация

Конфигурации сервера и клиента **разделены** — каждая живёт рядом со
своим исполняемым файлом, а не в одном общем файле.

### Сервер — `config.json` в корне репозитория

```json
{
    "host": "127.0.0.1",
    "port": 9002,
    "area": { "width": 100, "height": 100 },
    "seed": 54321,
    "terrain": { "...": "см. ниже" },
    "boulder_count": 40,
    "plants": { "...": "см. ниже" },
    "tick_interval_ms": 200,
    "snapshot_interval_ms": 100,
    "saves_dir": "saves"
}
```

- `host`, `port` — где сервер слушает WebSocket.
- `area` — размер Области в тайлах (04_WorldModel.md, п.2).
- `seed` — отправная точка случайности мира: рельеф, реки, булыжники, виды травы и первые семена. Один на весь мир, а не три отдельных (раньше были `terrain_seed`/`boulder_seed`/`plant_seed`): все три меняли одно и то же — "другой мир" — и только запутывали. Внутри генерации каждая стадия получает от него собственный поток случайности со смещением, чтобы близкие seed'ы не давали похожие узоры. Одинаковый seed задаёт одинаковое начальное состояние, но не одинаковую дальнейшую историю: мир недетерминирован (02_CorePrinciples.md, п.12a).
- `terrain` — все числовые параметры генерации почвы и водоёмов, подробности ниже.
- `boulder_count` — сколько непроходимых булыжников расставить (04_WorldModel.md, п.4).
- `plants` — виды травы и первое заселение мира растительностью, подробности ниже.
- `tick_interval_ms` — целевой интервал тика (06_GameLoop.md, п.4). Сколько тиков выполнить — не настройка: мир существует независимо от наблюдателя и тикает, пока жив сервер (02_CorePrinciples.md, п.1).
- `snapshot_interval_ms` — как часто состояние мира уходит клиентам. Это не тот же интервал, что `tick_interval_ms`: мир может тикать чаще, чем имеет смысл рисовать, и тогда рассылка каждый тик только копит очередь в сокете. `0` — рассылать на каждом тике.
- `saves_dir` — каталог сохранённых миров (по одному JSON-файлу на мир). Относительный путь — относительно каталога исполняемого файла сервера, не рабочей директории; абсолютный используется как есть. Каталог создаётся при первом сохранении.

Отсутствующие в файле поля берут значения по умолчанию — старый
`config.json` без новых полей остаётся рабочим, а не считается
невалидным целиком.

#### `terrain` — параметры генерации почвы и водоёмов

Метод (реализация — `core/src/generation/TerrainGenerator.cpp`): heightmap
на фрактальном шуме (fBm, OpenSimplex2) → реки как явные русла (у каждой
один случайный исток и один случайный конец на разных сторонах карты;
путь идёт курсом на цель с боковым отклонением от шума и лёгким
притяжением к более низкому рельефу — оба подавляются собственной
случайной скоростью реки, чем быстрее река, тем прямее; ширина и глубина
"дышат" вдоль пути через отдельный шум; река, упёршаяся в уже принятую,
либо сливается с ней и делает её шире ниже по течению, либо путь целиком
переигрывается — так русла разных рек не наезжают друг на друга нигде,
кроме точек слияния) — русло вырезается в heightmap ДО заливки впадин →
Priority-Flood (Barnes et al., 2014) для заполнения впадин (пруды,
естественно образующиеся в том числе поверх/вдоль уже вырезанного русла)
→ влажность через distance transform от воды. Ни одно число не зашито в
код — всё ниже читается из конфигурации.

```json
{
    "noise_frequency": 0.02,
    "noise_octaves": 4,
    "mountain_hardness": 0.6,
    "ice_cap_height": 0.75,
    "river_count": 3,
    "river_width": 3.0,
    "river_sinuosity": 0.5,
    "river_depth": 0.9,
    "pond_depth": 0.9,
    "minerals_average": 10.0,
    "water_source_count": 3,
    "water_source_depth": 2.0,
    "water_evaporation_rate": 0.0002,
    "rain_interval_ticks": 400,
    "rain_amount": 0.05,
    "soil_erosion_rate": 0.05,
    "max_erosion_depth": 0.5
}
```

Здесь только те числа, которые меняют видимый результат. Всё остальное —
форма самих законов (параметры fBm `lacunarity`/`gain`, уклон дна русла,
порог «это впадина, а не шум», затухание влажности, испарение, добавка за
уклон, сток за край карты, порог переноса минералов) — константы рядом с
местом использования в `core`, а не поля конфигурации: от мира к миру они
не менялись ни разу, но каждое тянулось через конфигурацию, сеть и файл
сохранения.

- `noise_frequency` — масштаб рельефа: частота fBm-шума высоты (меньше — крупнее формы, больше — мельче и чаще). Частоты остальных слоёв — каменистости, утрамбованности, минералов — фиксированные кратные от неё (×2.5, ×2, ×3): независимо они и не крутились, разный масштаб нужен только чтобы узоры слоёв не совпадали друг с другом.
- `noise_octaves` — сколько слоёв шума складывается: больше — мельче детали поверх крупных форм.
- `mountain_hardness` — насколько высота рельефа делает почву твёрдой: горы и их подножия сложены преимущественно камнем и слежавшимся грунтом. `0` — каменистость и утрамбованность целиком свои, от собственного шума; `1` — почти повторяют рельеф. Связь идёт именно в эту сторону: гора делает почву каменистой, а не каменистость поднимает гору (раньше было наоборот, `hardness_height_bump`). Обе сразу держать нельзя — это один и тот же круг; выбрана эта, потому что гора — в первую очередь скальный выход. Побочно она же и есть требование "где каменисто, реки быть не может": скала почти не размывается (мягкость при эрозии = `(1 - каменистость) × (1 - утрамбованность)`).
- `ice_cap_height` — высота, выше которой лежат вечные ледяные шапки: бесконечные источники воды и истоки всех рек (docs/01_Cosmology.md). Выше отметка — меньше ледников и меньше разных истоков; выше высшей точки карты — ледников в этом мире нет вовсе, и все реки начинаются с одной вершины (сервер печатает число ледниковых клеток в консоль, чтобы такой мир был виден сразу).
- `river_count` — сколько рек генерировать; каждая — явное русло (не эмерджентный порог) с истоком на леднике и устьем на краю мира. Русла разных рек не пересекаются друг с другом — либо явно сливаются (становясь шире), либо путь целиком переигрывается.
- `river_width`/`river_depth` — базовая ширина (тайлы) и глубина русла; оба чуть "дышат" вдоль пути за счёт встроенного шума (не параметр — не настраивается отдельно). Земля вплотную к руслу поднимается минимум на единицу над уровнем воды в нём: берег держит реку в русле сам, потому что выше собственного уровня вода подняться не может.
- `river_sinuosity` — базовая извилистость (0 — прямая линия, 1 — максимальный меандр; путь также слегка притягивается к более низкому рельефу). У каждой реки своя случайная доля виляния подавляет и то, и другое, поэтому реки одной карты не похожи одна на другую.
- `pond_depth` — средняя глубина воды пруда, в тех же единицах, что и `river_depth` (глубина тайла, не множитель). Где именно быть пруду и какого он размера, решает рельеф (Priority-Flood), а не фильтры по числу тайлов. Форма впадины внутри пруда неровная — центр глубже краёв; она нормируется на среднюю глубину впадины и умножается на `pond_depth`, поэтому итоговая средняя глубина воды по пруду равна ровно `pond_depth`, а форма впадины сохраняется как внутренний узор. Дно опускается вместе с глубиной (`elevation = filled - waterDepth`, где `filled` — уровень естественного перелива впадины), поэтому поверхность воды остаётся на этом уровне — пруд получает настоящую котловину, а не раздувается сам из себя над исходным рельефом.
- `minerals_average` — среднее количество минералов (`SoilComponent.minerals`) по карте; конкретное значение тайла — шум, в среднем сходящийся к этому числу. Отдельного значения для речных клеток нет: минералы разносит по карте течение (правило песочной кучи, `HydrologySystem`), и русло получает своё содержание само.
- `water_source_count` — сколько "родников" (`WaterSourceComponent`) разместить в случайных точках карты, помимо ледяной шапки на каждой вершине выше `ice_cap_height` (те получают источник автоматически). Чем родник является в мире, пока не решено — единственное место, у которого ещё нет причины в смысле 02_CorePrinciples.md, п.12 (см. docs/01_Cosmology.md, п.4).
- `water_source_depth` — глубина СТОЛБА воды источника, а не приток за тик. Ледник — неисчерпаемый запас, а не насос известной мощности: сколько бы из источника ни вытекло, к следующему тику он снова полон, и приток получается сам, ровно равным тому, что унесло течение. Свойство мира, а не параметр текущей симуляции: выбирается здесь, при генерации, записывается на World Entity (`WorldPropertiesComponent`) и во время симуляции не меняется — см. docs/06_GameLoop.md, п.1a. Раньше это был именно приток, и его приходилось подбирать вручную против испарения и стока: мало — исток пересыхал, много — карту заливало. Со столбом подбирать нечего; чем он выше, тем выше его поверхность и тем дальше он проталкивает воду по руслу.
- `water_evaporation_rate` — на сколько убывает за тик глубина каждой водной клетки. Вторая половина баланса воды, и держать её константой было нельзя: источники отдают столько, сколько унесёт течение, поэтому именно испарение (вместе с провалом за край мира) и решает, сколько воды карта в итоге держит. Слишком маленькое — карта, залитая целиком.
- `rain_interval_ticks`, `rain_amount` — раз во сколько тиков начинается дождь (`0` — дождей в этом мире нет) и какую глубину приносит одна капля. Дождь — приход воды извне Области (02_CorePrinciples.md, п.12b), а не перераспределение здешней. Сколько тиков он идёт и сколько капель падает за тик — не настройка, а форма закона (константы в `HydrologySystem.cpp`): дождь, заливавший разом всю карту, топил подчистую весь луг, поэтому редкие капли, растянутые по времени, — часть самого понятия "дождь", а не выбор конкретного мира. Упавшая капля дальше живёт по общему закону: стекает по уклону в низины и русла, испаряется, уходит за край.
- `soil_erosion_rate` — какая доля прошедшей через клетку воды превращается в вымытую породу. Тоже свойство мира. Вымытое оседает ниже по течению — в углублениях, куда вода этим тиком реально пришла, и ровно настолько, чтобы засыпать ступеньку вровень, не выше. Чему осесть негде — уходит с карты, как и вода за край: Область открыта (02_CorePrinciples.md, п.12b), и точного баланса почвы от неё не требуется. Скорость размыва дополнительно умножается на мягкость почвы — камень и утрамбованный грунт вымываются заметно медленнее рыхлой земли, поэтому горы (см. `mountain_hardness`) держатся, а рыхлая низина размывается. Эрозия происходит только там, где дно клетки ещё не ниже соседского: если оно уже ниже, вода и так течёт туда по уклону рельефа, и углублять нечего.
- `max_erosion_depth` — насколько глубже соседа, с которым клетка делится водой, её разрешено размыть. Тоже свойство мира. Без этого потолка клетка под постоянным источником размывается каждый тик без конца: высота уезжает в минус, и появляется бездонная яма, никак не связанная с рельефом вокруг.

Скорости течения среди настроек больше нет: вода не течёт с какой-то
скоростью, а встаёт на один уровень внутри "лужи" за один тик — см.
"Гидрология" ниже.

Влажность почвы отдельным слоем шума больше не задаётся и параметров не
имеет: это равновесие одного закона (`core/include/core/Moisture.hpp`) —
фон плюс близость воды, ослабленные каменистостью. Тот же закон служит
целью, к которой `HydrologySystem` тянет влажность каждый тик, поэтому
генерация ставит мир сразу в равновесие: раньше формула была написана
дважды с разными числами, и симуляция уводила только что созданную карту
к заметно более сухому состоянию (на стандартных настройках — средняя
влажность 0.81 сразу после генерации против равновесия 0.44).

#### `plants` — виды травы и первое заселение

Модель растений целиком описана в `docs/08_Plants.md`; здесь — только
настройки генерации. Реализация: `core/src/generation/PlantGenetics.cpp`
(виды и мутации), `core/src/generation/GrassSeeding.cpp` (первые семена),
`core/src/systems/PlantSystem.cpp` (жизнь растений каждый тик).

```json
{
    "grass_species": 5,
    "grass_coverage": 0.06,
    "mutation_rate": 0.06,
    "humus_decay_rate": 0.02
}
```

- `grass_species` — сколько видов травы в мире. Значение обрезается до
  3..12: меньше трёх видов не даёт конкуренции, больше двенадцати — виды
  перестают отличаться друг от друга при одном и том же бюджете
  преимуществ (см. ниже). Виды не косметические: у каждого свой набор
  биологических параметров, и они выбираются процедурно, а не заданы
  списком в коде.
- `grass_coverage` — какую долю клеток засеять при генерации. Это
  стартовая заселённость, а не итоговая: дальше трава расселяется сама и
  занимает всё, что ей подходит, поэтому даже с маленького значения луг
  за сотни тиков дорастает до тех же размеров.
- `mutation_rate` — насколько геном потомка может отличаться от
  родительского. Свойство мира (как `water_source_depth`), а не
  параметр текущей симуляции: выбирается при генерации, во время
  симуляции не меняется. Это доля *вложения* черты, а не доля её
  значения: у всех черт вложение живёт в одном и том же диапазоне
  `[0, 1]`, поэтому одна настройка одинаково означает "чуть-чуть" и для
  возраста в тиках, и для доли влаги за тик.
- `humus_decay_rate` — сколько крупиц минералов перегной возвращает в
  почву за тик. Тоже свойство мира. Маленькое значение по умолчанию
  намеренно: растение копило минералы сотни тиков, и возвращаться они
  должны не за один.

#### Растения: рост, размножение и перегной во время симуляции

`PlantSystem` (`core/src/systems/PlantSystem.cpp`) выполняется **каждый
тик**, сразу после `HydrologySystem` — растение должно видеть почву уже в
том состоянии, в которое её привела вода на этом тике.

- **Пригодность клетки** считается по каменистости и утоптанности:
  насколько почва близка к "своей" для этого генома и не слишком ли она
  утоптана. Клетка, залитая водой, непригодна полностью — трава на воде
  не растёт и гибнет за десяток тиков.
- **Влага.** Растение забирает долю влажности (`SoilComponent.moisture`)
  своей клетки в собственный запас — из сухой почвы взять нечего, поэтому
  забор пропорционален влажности. Расход на рост идёт из запаса, а не
  напрямую из почвы: пока запас есть, засуха росту не мешает, и именно
  запас позволяет пережить неблагоприятный период. Клетка от забора
  сохнет, поэтому чем гуще трава, тем суше под ней почва — это и есть
  конкуренция за воду. Влажность почвы — не запас воды, а состояние,
  которое `HydrologySystem` тянет к равновесию по близости к воде,
  поэтому у клетки есть предел, сколько влаги она способна отдавать
  бесконечно.
- **Минералы.** Целые крупицы уходят из `SoilComponent.minerals` в
  растение, но не больше, чем ему нужно на полный рост. Накопленные
  минералы ограничивают предельный размер: без них растение физически не
  может стать больше, сколько бы влаги у него ни было.
- **Недостаток ресурсов** не убивает мгновенно: он останавливает рост и
  копит стресс. Растение, которому долго нечем расти, погибает;
  переждавшее засуху на запасе — восстанавливается.
- **Размножение.** Созревшее, достаточно выросшее и не бедствующее
  растение с вероятностью `seed_chance` за тик роняет одно семя в
  соседнюю клетку — свободную от другого растения и непроходимых
  объектов, без воды, подходящую именно геному потомка и с минералами.
  Из подходящих клеток одна выбирается случайно, но тем чаще, чем лучше
  она потомку подходит: луг сам ползёт в сторону подходящей почвы.
  Взрывного заполнения не происходит — семя одно за тик, клетка должна
  быть свободна, а каждое семя стоит родителю биомассы, крупицы минералов
  и части запаса влаги, и потраченное нужно отрастить заново.
- **Смерть и перегной.** Растение умирает от старости или от накопленного
  стресса. Накопленные им минералы остаются на тайле перегноем
  (`HumusComponent` на том же Entity, что почва и вода) и возвращаются в
  почву по `humus_decay_rate` за тик; умершие на одной клетке растения
  складываются в один перегной. Плодородность клетки повышают именно эти
  возвращённые минералы.
- **Круговорот минералов**: почва -> растение -> перегной -> почва.
  Растение запасает не больше, чем нужно на полный рост, поэтому
  бесконечного накопления не возникает ни в растениях, ни в перегное.
  Законом сохранения это не является: мир открыт
  (02_CorePrinciples.md, п.12b), и минералы приходят и уходят помимо этого
  круга — их разносит по карте течение и уносит за границу Области.

Баланс видов держится не на ручных ограничениях, а на общем бюджете
преимуществ: каждая черта стоит бюджета тем больше, чем она сильнее, у
всех видов бюджет одинаковый, а мутация его не увеличивает (пересчитывает
обратно). Поэтому вид может быть лучше в одном только за счёт другого, а
удачные мутации не превращают линию в "лучшую во всём". Подробности и
известные ограничения модели — в `docs/08_Plants.md`.

#### Гидрология: почва и вода меняются во время симуляции

В отличие от `terrain` (разовая генерация), `HydrologySystem`
(`core/src/systems/HydrologySystem.cpp`) выполняется **каждый тик**,
сразу после `TimeSystem`:

- Влажность почвы (`SoilComponent.moisture`) медленно движется к
  равновесию, зависящему от расстояния до ближайшей воды и каменистости:
  рядом с водой растёт, вдали от неё — опускается к фоновому уровню.
  Формула равновесия одна на весь проект
  (`core/include/core/Moisture.hpp`), и генерация ставит мир сразу в неё —
  первый тик не начинает переписывать только что созданную карту.
- Утрамбованность (`SoilComponent.compaction`) рядом с водой постепенно
  размягчается — необратимо: если водоём уйдёт, участок останется мягким
  (без причины со стороны воды утрамбованность не меняется).
- **Вода находит свой уровень.** Единственный закон движения воды: берём
  клетку с водой и тех её восьмерых соседей, куда вода вообще может
  попасть, и разливаем всю воду этой "лужи" так, чтобы **поверхность**
  (`HeightComponent.height` + глубина воды) везде в ней стала одинаковой.
  Где дно ниже — глубже, где дно выше получившегося уровня — сухо.
  Ни направления стока, ни скорости течения, ни выбора "лучшего соседа" в
  мире больше нет — вместе с ними ушли и уклон, и добавки за глубину, и
  ползунок `water_flow_rate`.
  - Сосед участвует, если у него **уже есть вода** (лужи сливаются) или
    если его **дно ниже** текущей поверхности воды (воде есть куда
    пролиться). Второе условие — единственная дверь на сушу: выше
    собственного уровня вода подняться не может, поэтому берег на единицу
    выше кромки (генерация поднимает землю вдоль русла) держит реку в
    русле сам, без запретов "сюда не разливаться".
  - Внутри одной лужи выравнивание **полное, за один тик**. Лужи соседних
    клеток перекрываются, поэтому итоговая правка каждой клетки — сумма её
    правок по всем лужам, делённая на постоянное 9 (клетка + 8 соседей).
    Делитель именно постоянный: внутри лужи сумма правок равна нулю по
    построению, значит и по всей карте она остаётся нулевой — вода не
    появляется и не исчезает на кромке водоёма, где число задевающих
    клетку луж разное. Это же усреднение и гасит рябь, из-за которой
    прежний вариант с выбором одного соседа приходилось чинить в три
    прохода.
  - Правило одно и то же для любой воды — и реки, и пруда: "река" вообще
    не понятие для симуляции, это просто вода, которой есть или нет куда
    стекать (отдельного признака у `WaterComponent` нет). Форму русла —
    плавный спуск от ледника до края мира — задаёт генерация.
  - Тайл получает или теряет `WaterComponent`, когда глубина пересекает
    порог "здесь есть вода".
- **Источники — столбы воды постоянной глубины.** Ледяная шапка на вершине
  и родник каждый тик просто ставятся обратно на `water_source_depth`,
  сколько бы из них ни вытекло: это неисчерпаемый запас, а не насос
  известной мощности (docs/01_Cosmology.md).
- **Край мира — обрыв в пустоту.** Тайлы самой границы Области держатся на
  нулевой высоте и нулевой глубине: всё, что туда натекло, за тот же тик
  падает вниз и в мир не возвращается. Прежнего "стока за край" долей
  глубины больше нет — при нём вода у границы всё равно копилась, и
  скорость стока приходилось подбирать.
- Движение воды сопровождается **эрозией**: клетка, которая за тик воду
  ОТДАЛА, вымывается на долю `soil_erosion_rate` от отданного объёма.
  Размывается только та, чьё дно ещё не ниже соседского: если оно уже
  ниже, вода и так течёт туда по уклону самого рельефа, углублять нечего —
  русло сформировано. Эрозия остаётся там, где поток идёт лишь за счёт
  уровня воды (пруд стоит выше маленького порожка), то есть где почва
  действительно ещё мешает. Разная почва вымывается по-разному: множитель
  мягкости `(1 - каменистость) * (1 - утрамбованность)` — у голого камня
  почти ноль, у рыхлой земли почти единица. Поэтому горы держатся
  (`mountain_hardness`), размягчение почвы водой усиливает эрозию, а та
  сдвигает русло и берега, из-за чего очертания рек и прудов постепенно
  меняются. Глубина выемки ограничена `max_erosion_depth` относительно
  самого низкого соседа, с которым клетка делится водой: без потолка
  клетка под постоянным источником размывалась бы каждый тик без конца,
  уводя высоту в минус.
- Вымытая порода оседает ниже по течению: в тех клетках, которые за тик
  воду ПРИНЯЛИ, — ровно настолько, чтобы засыпать ступеньку до дна самого
  низкого соседа вровень, и ни крупицей выше (нанос не может создать новый
  бугор). Эрозия и осаждение — две ветки одного закона: отдала воду и дно
  не ниже соседского — порода мешает течению, вымываем; приняла воду, а
  рядом дно выше — здесь углубление, туда ложится нанос. Чему осесть
  негде, уходит с карты вместе с водой: Область — открытый кусок мира, а
  не замкнутый сосуд (02_CorePrinciples.md, п.12b), и точного баланса
  почвы от неё не требуется.
- Дожди: раз в `rain_interval_ticks` тиков идёт дождь, роняя редкие капли
  по `rain_amount` глубины в случайные клетки — приход воды извне Области.
  Отдельного "погодного" состояния у мира нет: идёт ли сейчас дождь и куда
  падают капли, разыгрывается от номера тика и seed мира, поэтому погоде
  не нужна собственная память помимо самого мира и сохранять в файл её не
  приходится.
- Минералы (`SoilComponent.minerals`, целое число) двигаются между
  соседними тайлами: каждый тик тайл A ищет среди соседей, которые
  "притягивают" минералы (есть вода или влажность выше порога),
  самого бедного минералами B; если A
  богаче B минимум на 2, к B уходит ровно половина разницы (целочисленно)
  — 8 и 6 становятся 7 и 7, 10 и 6 — 8 и 8. Ровно один сосед за тик, не
  несколько: если считать перетоки к нескольким соседям одновременно по
  одному и тому же снимку, тайл может отдать больше, чем у него есть, и
  вместо предсказуемого сглаживания получаются на вид хаотичные "волны".
- Каждый тик всякая вода теряет немного глубины на испарение. Вместе с
  провалом за край мира это весь отток; приток же не задан числом — сколько
  унесёт течение, столько источники и отдадут. Поэтому именно испарение и
  решает, сколько воды карта в итоге держит.

Скорости этих процессов (кроме глубины столба источников, испарения,
дождей, скорости эрозии и потолка выемки — свойств мира, см. выше) —
внутренние константы в `HydrologySystem.cpp` (не параметры конфигурации,
как и часть механики генерации рек) — подобраны так, чтобы изменения были
заметны за десятки-сотни тиков, а не мгновенно.

### Клиент — `config.json` рядом с `client`/`client.exe`

Клиент **сам создаёт** этот файл при первом запуске, если его нет —
ничего настраивать заранее не нужно:

```json
{
    "host": "127.0.0.1",
    "port": 9002,
    "tile_size": 16,
    "window_width": 1280,
    "window_height": 720,
    "fullscreen": false,
    "show_rockiness": true,
    "show_compaction": true,
    "show_moisture": true,
    "show_minerals": true,
    "show_height": true,
    "show_plants": true,
    "zoom": 1.0,
    "show_generation_panel": false
}
```

- `host`, `port` — куда подключаться (адрес сервера).
- `tile_size` — базовый размер тайла на экране мира, в пикселях; поверх него работает масштаб (`zoom`).
- `window_width`, `window_height`, `fullscreen` — экран Settings; сохраняются автоматически при изменении.
- `show_*`, `zoom`, `show_generation_panel` — состояние экрана мира: какие слои включены, во сколько раз увеличена карта и открыта ли панель параметров. Сохраняется между запусками, чтобы каждый раз не подбирать заново одно и то же. Позиция прокрутки не сохраняется — осмысленной точкой отсчёта она была бы только для конкретного мира, а после запуска клиента мир может оказаться другим.

И сервер, и клиент принимают путь к своей конфигурации первым аргументом
(`server other_config.json`, `client other_config.json`) — если аргумент
не передан, используется `config.json` рядом с самим исполняемым файлом
(создаётся автоматически, если отсутствует). `run.sh` передаёт
серверу путь до корневого `config.json`, а клиента запускают без
аргумента — он найдёт/создаст свой сам.

## Зависимости

EnTT, nlohmann/json, IXWebSocket и raylib (только для клиента) лежат
прямо в репозитории — `third_party/` в корне. Ни один CMake-проект в
этом репозитории (ни `server`, ни `clients/desktop`) не обращается к
сети при конфигурации или сборке. `third_party/CMakeLists.txt` —
единственное место, где описано, как их собирать; и корневой
`CMakeLists.txt` (для core/server), и `clients/desktop/CMakeLists.txt`
подключают именно его через `add_subdirectory`, чтобы код и описание
сборки библиотек не повторялись в двух местах. raylib собирается только
для клиента (сервер остаётся headless, без графики/X11/OpenGL) — это
регулируется опцией `GOBLINS_WITH_RAYLIB`, которую включает только
`clients/desktop/CMakeLists.txt`. Так же устроен `shared/` — общий код
(чтение конфигурации, определение пути к своему исполняемому файлу),
который использует и сервер, и клиент.

Системных зависимостей (OpenSSL, zlib, Qt) не требуется — TLS и сжатие
WebSocket-сообщений отключены за ненадобностью на этом этапе (всё
рассчитано на локальную сеть); аудио-модуль raylib отключён (звук в
проекте не используется). На Linux для сборки клиента нужны стандартные
dev-пакеты X11/OpenGL (libx11-dev, libxrandr-dev, libxinerama-dev,
libxcursor-dev, libxi-dev, libgl1-mesa-dev) — на Windows ничего
дополнительно ставить не нужно, всё уже есть в системе.

## Сервер

### Сборка

```
mkdir build && cd build
cmake ..
cmake --build . -j
```

### Запуск

```
./server/server [путь до config.json]
```

По умолчанию ищет (и создаёт, если нет) `config.json` рядом с собой.
Программа поднимает WebSocket-сервер и ждёт: мир при старте не
генерируется и игровой цикл стоит на паузе, пока клиент не пришлёт
`start_simulation` (создать новый мир или загрузить сохранённый). Дальше
сервер тикает и рассылает подключённым клиентам изменения состояния —
`HydrologySystem` меняет почву и воду непрерывно, поэтому клиенту нужно
видеть не только номер тика (подробности — в протоколе ниже). Весь
консольный вывод — на английском (чтобы не зависеть от кодировки консоли).
`Ctrl+L` в консоли сервера включает и выключает построчный вывод тиков.

### Протокол (WebSocket, JSON), версия 13

Состояние мира уходит клиенту двумя разными сообщениями, потому что
состоит из двух разных по природе частей: того, что между регенерациями не
меняется вообще, и того, что меняется каждый тик.

**`world_init`** — всё, из чего клиент строит мир с нуля. Шлётся при
подключении, после регенерации и после загрузки/создания мира:

```json
{"type": "world_init", "area": {"width": 100, "height": 100}, "tick": 0,
 "paused": false, "world": "world-20260812-200716",
 "scale": 1000,
 "seed": 54321, "terrain": {"...": "все поля из config.json/terrain"},
 "boulder_count": 40,
 "plants": {"...": "все поля из config.json/plants"},
 "constants": [{"group": "Hydrology", "name": "kWaterSlopeBoost", "value": 5.0}, "..."],
 "boulders": [{"x": 12, "y": 34}, "..."],
 "water_sources": [{"x": 5, "y": 5}, "...истоки рек + \"родники\"..."],
 "plant_species": [{"species": 0, "max_age": 1740.5, "...": "все черты генома по именам"}],
 "layers": {"rockiness": [], "moisture": [], "compaction": [], "minerals": [],
            "height": [], "water": [], "humus": [], "species": [], "growth": []}}
```

- `seed`/`terrain`/`boulder_count`/`plants` — это ровно тот же набор, что
  клиент присылает обратно в `regenerate`: панель параметров строится из
  этого сообщения целиком, без вкомпилированных в клиент умолчаний.
- `layers` — плоские массивы **целых**, row-major, по одному значению на
  тайл. Целые, а не float: в JSON число с плавающей точкой печатается как
  double (два десятка знаков), а массив здесь — на всю Область. `moisture`,
  `compaction`, `rockiness`, `height` и `water` — в тысячных долях (делить
  на `scale`), `growth` — целые проценты, `minerals` и `humus` — счётные
  величины как есть, `species` — индекс вида или `-1` (клетка пуста).
  `water == 0` значит "воды нет" (у тайла просто нет `WaterComponent`),
  `humus == 0` — "перегноя нет".
- `constants` — числа, зашитые в законы мира (`core/Diagnostics.hpp`): они
  не настраиваются и не меняются, клиент показывает их только для чтения
  (оверлей по клавише `C`). Едут здесь же, потому что `world_init` по
  определению содержит всё, из чего строится картина мира.
- Состав генома в протоколе не фиксирован — сервер перечисляет черты по
  именам, клиент показывает то, что пришло, поэтому новая черта не требует
  правок в клиенте.
- `world` — имя мира, который сейчас в памяти сервера; пустая строка
  означает, что он ещё не сохранён (например, только что перегенерирован).

**`world_delta`** — не чаще `snapshot_interval_ms` и только если что-то
изменилось (на паузе не шлётся вовсе):

```json
{"type": "world_delta", "tick": 31, "paused": false,
 "moisture": [1204, 512, 1205, 498, "...пары индекс-значение..."], "water": ["..."]}
```

Те же слои, что в `layers`, кроме статических (каменистость, булыжники,
источники и виды травы меняются только регенерацией, а она шлёт новый
`world_init`). Пары "индекс тайла — новое значение", только изменившиеся
клетки; слой без изменений в сообщение не попадает вовсе. Полный снапшот
на каждый тик означал бы десятки тысяч чисел пять раз в секунду ради
нескольких сотен изменившихся клеток — а очередь отправки сокета
неограниченна, и клиент, не успевающий принимать, отставал бы всё сильнее:
счётчик тика продолжал бы расти уже после остановки мира. По той же
причине рассылка пропускается целиком, если у кого-то из клиентов очередь
отправки слишком велика; точка отсчёта при этом не сдвигается, и
пропущенные изменения войдут в следующую дельту.

Остальные сообщения сервера:

```json
{"type": "world_list", "current": "world-20260812-200716",
 "worlds": [{"name": "world-20260812-200716", "tick": 30,
             "area_width": 100, "area_height": 100, "seed": 54321,
             "created_at": "2026-08-12T20:07:16Z",
             "saved_at": "2026-08-12T20:09:02Z"}, "...свежие сверху..."]}
{"type": "pause_state", "paused": true}
{"type": "notice", "level": "info", "text": "World saved as '...' (tick 30)."}
```

`world_list` шлётся при подключении и после каждой записи или удаления
мира; `pause_state` — всем клиентам при изменении паузы; `notice` — то,
что нужно показать пользователю по итогам операции без собственного ответа
(сохранение, загрузка, удаление), особенно при ошибке.

Клиент → сервер:

```json
{"type": "toggle_pause"}
{"type": "stop_simulation"}
{"type": "list_worlds"}
{"type": "save_world", "name": ""}
{"type": "delete_world", "name": "world-20260812-200716"}
{"type": "start_simulation", "world": "world-20260812-200716"}
{"type": "regenerate", "params": {"seed": 777, "terrain": {}, "boulder_count": 40, "plants": {}}}
{"type": "save_generation_config", "params": {"...": "то же, что в regenerate"}}
```

- `stop_simulation` — не переключатель, а гарантированная пауза (кнопка
  "Back" на экране мира).
- `save_world` с пустым `name` — под именем текущего мира, а если мир ещё
  не сохранялся, сервер придумает новое.
- `start_simulation` с именем — загрузить сохранённый мир (размер его
  Области может отличаться от `area` в конфигурации); без имени —
  сгенерировать новый текущими параметрами. На диск он при этом не
  пишется.
- `regenerate` — полностью пересоздать мир (все Entity, номер тика — в 0) и
  разослать свежий `world_init` всем клиентам.
- `save_generation_config` — записать присланные параметры в `config.json`
  сервера, чтобы они стали умолчанием при следующем запуске. Сохраняется
  именно присланное — то, что набрано на панели, даже если мир этими
  значениями ещё не перегенерирован.
- Отсутствующие в `params` поля берут значения по умолчанию, а не делают
  запрос невалидным — так же, как в конфигурации.

Имя мира — имя файла сохранения без расширения; сервер проверяет его
(только буквы/цифры/`-`/`_`/`.`/пробел) и отвергает всё, что могло бы
увести за пределы каталога сохранений.

Сохранение, загрузка, удаление и генерация выполняются на потоке
`GameLoop` между тиками: запись читает весь ECS registry, а загрузка его
перезаписывает — делать это параллельно с выполняющимся тиком нельзя.

Пауза настоящая, а не косметическая: пока мир на паузе, `GameLoop` не
выполняет ни одной системы и не рассылает тиков — это распространяется на
всех подключённых клиентов одновременно (07_TechStack.md, все
взаимодействия — через интерфейсы, единый источник истины о состоянии
паузы — на сервере).

### Сохранённые миры

Один мир — один файл `<имя>.json` в каталоге `saves_dir` (см.
конфигурацию). Имя файла без расширения и есть идентификатор мира: список
миров не зависит от содержимого файлов, а два мира не могут случайно
оказаться с одним именем. Реализация — `server/src/WorldSave.cpp`; в
`core` этого кода нет, потому что ядро не знает ни о файлах, ни о JSON
(07_TechStack.md, п.6).

Сохраняется **полное состояние мира** — все Entity со всеми компонентами
(включая World Entity с номером тика), а не только seed генерации: мир
после N тиков повторной генерацией уже не восстанавливается. Индекс
размещения по тайлам (`Area`) в файл не пишется — он выводится из
`PositionComponent`/`ImpassableComponent` и перестраивается при загрузке.

```json
{"format": "goblins_world", "version": 1,
 "info": {"name": "...", "tick": 0, "area_width": 100, "area_height": 100,
          "seed": 54321, "created_at": "...", "saved_at": "..."},
 "generation": {"seed": 54321, "terrain": {...},
                "boulder_count": 40, "plants": {...}},
 "entities": [{"position": {"x": 0, "y": 0},
               "soil": {"moisture": 0.42, "rockiness": 0.1, "compaction": 0.3, "minerals": 10},
               "height": 0.57,
               "water": {"depth": 1.4},
               "water_source": true,
               "humus": {"minerals": 3, "pending": 0.4}},
              {"position": {"x": 12, "y": 34}, "impassable": true},
              {"position": {"x": 8, "y": 20},
               "plant": {"age": 120.0, "growth": 0.6, "moisture": 0.3,
                          "minerals": 3, "mineral_pending": 0.2, "stress": 0.0},
               "genome": {"species": 1, "max_age": 1740.5, "...": "все черты по именам"}},
              {"time": {"tick": 0},
               "world_properties": {"water_source_depth": 2.0,
                                     "water_evaporation_rate": 0.0002,
                                     "rain_interval_ticks": 400, "rain_amount": 0.05,
                                     "soil_erosion_rate": 0.05,
                                     "max_erosion_depth": 0.5,
                                     "plant_mutation_rate": 0.06, "humus_decay_rate": 0.02,
                                     "plant_random_seed": 24680},
               "plant_species": [{"species": 0, "...": "архетип вида"}]}]}
```

Формат прирастает без смены версии: `height` (`HeightComponent`),
`soil.minerals`, `water_source` (`WaterSourceComponent`),
`world_properties` (`WorldPropertiesComponent` — свойства мира,
docs/06_GameLoop.md, п.1a), а также `plant`/`genome`, `humus` и
`plant_species` (растения, docs/08_Plants.md) добавлялись именно так.
Отсутствующее поле берёт значение по умолчанию (высота 0, минералы 0, не
источник, свойства мира — из `WorldPropertiesComponent`; растений в таком
мире просто нет, и трава в нём не появится, пока мир не перегенерировать).
Поля, которых больше нет в модели мира — `water.flow_speed` у воды, снятые
с `world_properties` пороги, ставшие константами, и старые
`terrain_seed`/`boulder_seed`/`plant_seed` в `generation` — в старых файлах
молча игнорируются: лишний ключ не делает файл нечитаемым. У миров,
сохранённых до объединения seed'ов, три прежних числа обратно в одно всё
равно не сходятся, поэтому такой мир на диске (сами Entity) не страдает, а
неточной оказывается только надпись "чем сгенерирован" в панели. Отдельные
черты генома тоже читаются по именам: черта, которой в старом файле нет,
берёт значение по умолчанию, а не ломает загрузку.

Растений на заросшей карте тысячи, и каждое — Entity с собственным
геномом, поэтому файл мира с лугом заметно больше файла голой карты.

Мир сохраняется сразу после генерации — с нулевым тиком, то есть ровно в
том состоянии, в каком он появился на свет, ещё до первого тика. Дальше
его можно сохранять сколько угодно раз кнопкой "Save world": запись идёт
поверх того же файла (`created_at` при этом сохраняется, `saved_at` и
`tick` обновляются), а сама запись атомарная — через временный файл с
переименованием, чтобы прерванное сохранение не портило предыдущую
версию мира.

## Десктопный клиент

Отдельный CMake-проект в `clients/desktop` — собирается независимо от
сервера (свой `add_subdirectory` на общие `third_party/` и `shared/`, см.
выше). Графическое приложение на raylib.

### Сборка

```
cd clients/desktop
mkdir build && cd build
cmake ..
cmake --build . -j
```

### Запуск

Сначала должен быть запущен сервер. Затем:

```
./client [путь до config.json]
```

По умолчанию ищет (и создаёт, если нет) `config.json` рядом с собой и
подключается к `host:port` из него.

## Структура

- `config.json` — конфигурация сервера (у клиента своя, рядом с его бинарником).
- `third_party/` — vendored-зависимости (EnTT, nlohmann/json, IXWebSocket, raylib), общие для core/server и клиента.
- `shared/` — общий код (конфигурация, путь к исполняемому файлу, описание сохранённого мира в протоколе), общий для server и client.
- `core/` — ядро симуляции: ECS (EnTT), компоненты, системы, игровой цикл, генерация мира. Состав мира — какие этапы порождают его и какие законы действуют каждый тик — тоже здесь (`core/Simulation.hpp`): это свойства мира, а не запускающей его программы. Не зависит от server/clients.
- `server/` — исполняемый файл `server`, оборачивающий core: игровой цикл, WebSocket-слой (IXWebSocket + nlohmann/json) и сохранение/загрузка миров (`WorldSave`).
- `clients/desktop/` — исполняемый файл `client`, графическое приложение на raylib. Получает данные только по WebSocket-протоколу сервера.
- `clients/web/` — будущий браузерный клиент.
- `docs/` — архитектурные документы проекта. `01_Cosmology.md` — устройство
  мира как целого: остров в пустоте, горы из камня, ледники как истоки воды.
- `build.sh`/`run.sh` — сборка и запуск сервера+клиента одной командой (на Windows — из Git Bash/WSL).
