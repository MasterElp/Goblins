World simulator
# Главная идея
- Проект представляет собой автономную симуляцию живого мира.
- Основой проекта является не игровой процесс, а моделирование мира, который способен существовать, развиваться и изменяться независимо от присутствия игрока.
- Игрок не является центром мира. Он лишь один из возможных наблюдателей или участников происходящих событий.

# Goblins

Симуляция мира. Архитектура и философия проекта — в `docs/`.

## Быстрый старт

Windows (PowerShell):
```
.\build.ps1
.\run.ps1
```

Linux/macOS (или Windows через Git Bash/WSL — но см. предупреждение ниже):
```
./build.sh
./run.sh
```

`build.*` собирает и server, и client. `run.*` поднимает сервер в фоне
(или в отдельном окне на Windows), ждёт, пока он займёт порт, запускает
клиента и сам останавливает сервер по завершении клиента (или по Ctrl+C).

**На Windows используй именно `.ps1`, не `.sh` через Git Bash.** Клиент —
интерактивная консольная программа (`_kbhit`/`_getch` для чтения клавиш,
ANSI-коды для очистки экрана), а Git Bash запускает процессы под mintty,
который не даёт настоящую Win32-консоль — в результате вместо перерисовки
экран просто скроллится вниз. `.sh`-скрипты оставлены для Linux/macOS/WSL,
где это не проблема.

## Конфигурация

Один файл на корню репозитория — `config.json`. Его читают и сервер, и
клиент, поэтому адрес и порт не расходятся:

```json
{
    "host": "127.0.0.1",
    "port": 9002,

    "area": { "width": 100, "height": 100 },

    "boulder_count": 40,
    "boulder_seed": 12345,

    "tick_interval_ms": 200,
    "tick_count": -1,

    "view": { "width": 60, "height": 25 },
    "scroll_step": 5
}
```

- `host`, `port` — где сервер слушает WebSocket и куда подключается клиент.
- `area` — размер Области в тайлах (04_WorldModel.md, п.2).
- `boulder_count`, `boulder_seed` — сколько непроходимых булыжников и с каким seed их генерировать (04_WorldModel.md, п.4); один и тот же seed даёт одну и ту же карту.
- `tick_interval_ms` — целевой интервал тика (06_GameLoop.md, п.4).
- `tick_count` — сколько тиков выполнить; `-1` — бесконечно (мир существует независимо от наблюдателя, 02_CorePrinciples.md, п.1).
- `view`, `scroll_step` — размер окна просмотра клиента в символах и шаг прокрутки по WASD.

Если файла нет или в нём не хватает поля — используется значение по
умолчанию (те же, что в примере выше), а не ошибка.

И сервер, и клиент принимают путь к конфигурации первым аргументом
(`./server other_config.json`) — по умолчанию ищут `config.json` в
текущей рабочей директории. `run.sh`/`run.ps1` сами передают абсолютный
путь до корневого `config.json`, так что это не зависит от того, откуда
их запускают.

## Зависимости

EnTT, nlohmann/json и IXWebSocket лежат прямо в репозитории —
`third_party/` в корне. Ни один CMake-проект в этом репозитории (ни
`server`, ни `clients/desktop`) не обращается к сети при конфигурации
или сборке. `third_party/CMakeLists.txt` — единственное место, где
описано, как их собирать; и корневой `CMakeLists.txt` (для core/server),
и `clients/desktop/CMakeLists.txt` подключают именно его через
`add_subdirectory`, чтобы код и описание сборки библиотек не повторялись
в двух местах. Так же устроен `shared/` — общий код чтения конфигурации,
который использует и сервер, и клиент.

Системных зависимостей (OpenSSL, zlib, Qt) не требуется — TLS и сжатие
WebSocket-сообщений отключены за ненадобностью на этом этапе (всё
рассчитано на локальную сеть).

## Сервер

### Сборка

```
mkdir build && cd build
cmake ..
cmake --build . -j
```

### Запуск

```
./server/server [путь до config.json]
```

По умолчанию ищет `config.json` в текущей директории. Программа создаёт
Область, случайно размещает булыжники (без коллизий по тайлам), поднимает
WebSocket-сервер и запускает игровой цикл, рассылая номер каждого тика
подключённым клиентам. Весь консольный вывод — на английском (чтобы не
зависеть от кодировки консоли).

### Протокол (WebSocket, JSON)

Сервер → клиент, сразу при подключении:
```json
{"type": "world_snapshot", "area": {"width": 100, "height": 100}, "tick": 0,
 "boulders": [{"x": 12, "y": 34}, ...]}
```

Сервер → клиент, после каждого тика:
```json
{"type": "tick", "tick": 5}
```

## Десктопный клиент

Отдельный CMake-проект в `clients/desktop` — собирается независимо от
сервера (свой `add_subdirectory` на общие `third_party/` и `shared/`, см.
выше). Чистый C++, без GUI-фреймворка: рендер — в терминал.

### Сборка

```
cd clients/desktop
mkdir build && cd build
cmake ..
cmake --build . -j
```

### Запуск

Сначала должен быть запущен сервер. Затем:

```
./client [путь до config.json]
```

По умолчанию ищет `config.json` в текущей директории и подключается к
`host:port` из него. В терминале рисуется окно карты (`view.width` x
`view.height` символов; `.` — пустой тайл, `#` — булыжник), сверху —
текущий тик и координаты окна просмотра. Управление: `W`/`A`/`S`/`D` —
прокрутка на `scroll_step` тайлов, `Q` — выход. Вывод — на английском.

## Структура

- `config.json` — единая конфигурация сервера и клиента.
- `third_party/` — vendored-зависимости (EnTT, nlohmann/json, IXWebSocket), общие для core/server и клиента.
- `shared/` — общий код (чтение конфигурации), общий для server и client.
- `core/` — ядро симуляции: ECS (EnTT), компоненты, системы, игровой цикл, генерация мира. Не зависит от server/clients.
- `server/` — исполняемый файл `server`, оборачивающий core: игровой цикл + WebSocket-слой (IXWebSocket + nlohmann/json).
- `clients/desktop/` — исполняемый файл `client`, консольный клиент на чистом C++. Получает данные только по WebSocket-протоколу сервера.
- `clients/web/` — будущий браузерный клиент.
- `docs/` — архитектурные документы проекта.
- `build.sh`/`run.sh` (Linux/macOS) и `build.ps1`/`run.ps1` (Windows) — сборка и запуск сервера+клиента одной командой.
