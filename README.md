World simulator
# Главная идея
- Проект представляет собой автономную симуляцию живого мира.
- Основой проекта является не игровой процесс, а моделирование мира, который способен существовать, развиваться и изменяться независимо от присутствия игрока.
- Игрок не является центром мира. Он лишь один из возможных наблюдателей или участников происходящих событий.

# Goblins

Симуляция мира. Архитектура и философия проекта — в `docs/`.

## Быстрый старт

Windows:
```
build.bat
run.bat
```

Linux/macOS:
```
./build.sh
./run.sh
```

`build.*` собирает и server, и client. `run.*` поднимает сервер в фоне
(на Windows — в отдельном окне консоли), ждёт, пока он займёт порт,
запускает клиента (открывается окно) и сам останавливает сервер по
завершении клиента (или по Ctrl+C).

На Windows — именно `.bat`, не PowerShell-скрипты: `.bat` не требует
менять политику выполнения скриптов, ничего дополнительно разрешать не
нужно, просто двойной клик или запуск из `cmd`.

## Клиент — графическое приложение

Клиент — окно (raylib), не консоль: карта отрисовывается тайлами, вверху
— полупрозрачная панель с номером тика, размером Области и текущими
координатами окна просмотра. Тайл под курсором мыши подсвечивается, его
координаты и параметры почвы (влажность/каменистость/утрамбованность,
глубина воды если есть) показаны в правом верхнем углу панели.

Каждый тайл окрашен смешением почвенных параметров (каменистость и
утрамбованность задают материал, влажность затемняет поверх), вода —
отдельным сине-бирюзовым оттенком, темнее с глубиной; булыжники —
маленькие тёмные квадраты поверх почвы.

Управление:
- `W`/`A`/`S`/`D` или стрелки — плавная прокрутка.
- `P` — пауза/возобновление мира. Это не локальная заморозка картинки, а
  настоящая команда серверу: пока мир на паузе, `GameLoop` не выполняет
  тиков вообще, и это видят все подключённые клиенты одновременно (в углу
  экрана появляется отметка `PAUSED`).
- `TAB` — панель настроек генерации (справа).
- Закрыть окно — как обычное приложение.

### Панель настроек генерации

Открывается по `TAB`. Показывает все параметры из `terrain` (см. ниже) в
виде ползунков, плюс seed'ы (со случайной перегенерацией по кнопке
"Random") и число булыжников. При старте панель заполняется текущими
параметрами сервера — так видно, чем именно сгенерирован мир, который
сейчас на экране.

Кнопка **Regenerate** отправляет серверу
`{"type": "regenerate", "params": {...}}`. Сервер — единственный источник
истины: он удаляет прежние Entity почвы/воды/булыжников, генерирует
заново на том же месте (размер Области не меняется — для этого нужен
перезапуск с новым `area` в конфигурации) и рассылает свежий снапшот
**всем** подключённым клиентам, не только тому, кто нажал кнопку.
Регенерация выполняется на потоке игрового цикла между тиками, не
прерывая его: тик просто продолжается со следующего номера.

Кнопка **Reset to current server state** отбрасывает несохранённые правки
и возвращает ползунки к текущему состоянию сервера.

## Конфигурация

Конфигурации сервера и клиента **разделены** — каждая живёт рядом со
своим исполняемым файлом, а не в одном общем файле.

### Сервер — `config.json` в корне репозитория

```json
{
    "host": "127.0.0.1",
    "port": 9002,
    "area": { "width": 100, "height": 100 },
    "terrain_seed": 54321,
    "terrain": { "...": "см. ниже" },
    "boulder_count": 40,
    "boulder_seed": 12345,
    "tick_interval_ms": 200,
    "tick_count": -1
}
```

- `host`, `port` — где сервер слушает WebSocket.
- `area` — размер Области в тайлах (04_WorldModel.md, п.2).
- `terrain_seed` — seed для генерации почвы/рек/прудов; один и тот же seed даёт один и тот же результат.
- `terrain` — все числовые параметры генерации почвы и водоёмов, подробности ниже.
- `boulder_count`, `boulder_seed` — сколько непроходимых булыжников и с каким seed их генерировать (04_WorldModel.md, п.4); один и тот же seed даёт одну и ту же карту.
- `tick_interval_ms` — целевой интервал тика (06_GameLoop.md, п.4).
- `tick_count` — сколько тиков выполнить; `-1` — бесконечно (мир существует независимо от наблюдателя, 02_CorePrinciples.md, п.1).

#### `terrain` — параметры генерации почвы и водоёмов

Метод (реализация — `core/src/generation/TerrainGenerator.cpp`): heightmap
на фрактальном шуме (fBm, OpenSimplex2) → Priority-Flood (Barnes et al.,
2014) для заполнения впадин (пруды) → D8 flow accumulation по
заполненному рельефу (реки) → влажность через distance transform от воды.
Ни одно число не зашито в код — всё ниже читается из конфигурации.

```json
{
    "height_noise_frequency": 0.02,
    "rock_noise_frequency": 0.05,
    "compaction_noise_frequency": 0.04,
    "moisture_noise_frequency": 0.03,
    "noise_octaves": 4,
    "noise_lacunarity": 2.0,
    "noise_gain": 0.5,
    "rock_height_bump": 0.35,
    "compaction_height_bump": 0.25,
    "river_threshold": 55.0,
    "river_depth_base": 0.3,
    "river_depth_range": 2.2,
    "edge_inflow_max": 45.0,
    "min_pond_depth": 0.01,
    "min_pond_size": 1,
    "max_pond_size": 0,
    "pond_depth_scale": 4.0,
    "moisture_falloff": 8.0,
    "water_moisture_boost": 0.7,
    "rock_moisture_reduction": 0.3
}
```

- `*_noise_frequency` — частота fBm-шума для каждого слоя (меньше — крупнее пятна/формы, больше — мельче и чаще).
- `noise_octaves`/`noise_lacunarity`/`noise_gain` — параметры фрактального шума, общие для всех слоёв.
- `rock_height_bump`, `compaction_height_bump` — насколько каменистость/утрамбованность поднимают высоту рельефа (вода физически огибает такие участки — этим и обеспечивается требование "где утрамбовано и каменисто, реки быть не может", без ручных исключений).
- `river_threshold` — порог накопления стока (D8), выше которого клетка — река; `river_depth_base`/`river_depth_range` — диапазон глубины реки.
- `edge_inflow_max` — максимальный случайный бонус к накоплению стока на граничных клетках (river может "начинаться" за краем карты).
- `min_pond_depth` — минимальная глубина впадины, чтобы считаться прудом.
- `min_pond_size`/`max_pond_size` — допустимый размер связной области пруда в тайлах; `max_pond_size: 0` — без верхнего ограничения.
- `pond_depth_scale` — множитель глубины пруда (глубина впадины × этот коэффициент).
- `moisture_falloff` — за сколько тайлов влияние воды на влажность спадает примерно вдвое.
- `water_moisture_boost` — насколько вода поднимает влажность рядом с собой.
- `rock_moisture_reduction` — насколько каменистая почва хуже держит влагу.

### Клиент — `config.json` рядом с `client`/`client.exe`

Клиент **сам создаёт** этот файл при первом запуске, если его нет —
ничего настраивать заранее не нужно:

```json
{
    "host": "127.0.0.1",
    "port": 9002,
    "view": { "width": 60, "height": 25 },
    "scroll_step": 5,
    "tile_size": 16
}
```

- `host`, `port` — куда подключаться (адрес сервера).
- `view` — сколько тайлов видно в окне просмотра (ширина x высота).
- `scroll_step` — скорость прокрутки, тайлов в секунду при зажатой клавише.
- `tile_size` — размер одного тайла на экране, в пикселях (отсюда и размер окна: `view.width * tile_size` x `view.height * tile_size`).

И сервер, и клиент принимают путь к своей конфигурации первым аргументом
(`server other_config.json`, `client other_config.json`) — если аргумент
не передан, используется `config.json` рядом с самим исполняемым файлом
(создаётся автоматически, если отсутствует). `run.sh`/`run.bat` передают
серверу путь до корневого `config.json`, а клиента запускают без
аргумента — он найдёт/создаст свой сам.

## Зависимости

EnTT, nlohmann/json, IXWebSocket и raylib (только для клиента) лежат
прямо в репозитории — `third_party/` в корне. Ни один CMake-проект в
этом репозитории (ни `server`, ни `clients/desktop`) не обращается к
сети при конфигурации или сборке. `third_party/CMakeLists.txt` —
единственное место, где описано, как их собирать; и корневой
`CMakeLists.txt` (для core/server), и `clients/desktop/CMakeLists.txt`
подключают именно его через `add_subdirectory`, чтобы код и описание
сборки библиотек не повторялись в двух местах. raylib собирается только
для клиента (сервер остаётся headless, без графики/X11/OpenGL) — это
регулируется опцией `GOBLINS_WITH_RAYLIB`, которую включает только
`clients/desktop/CMakeLists.txt`. Так же устроен `shared/` — общий код
(чтение конфигурации, определение пути к своему исполняемому файлу),
который использует и сервер, и клиент.

Системных зависимостей (OpenSSL, zlib, Qt) не требуется — TLS и сжатие
WebSocket-сообщений отключены за ненадобностью на этом этапе (всё
рассчитано на локальную сеть); аудио-модуль raylib отключён (звук в
проекте не используется). На Linux для сборки клиента нужны стандартные
dev-пакеты X11/OpenGL (libx11-dev, libxrandr-dev, libxinerama-dev,
libxcursor-dev, libxi-dev, libgl1-mesa-dev) — на Windows ничего
дополнительно ставить не нужно, всё уже есть в системе.

## Сервер

### Сборка

```
mkdir build && cd build
cmake ..
cmake --build . -j
```

### Запуск

```
./server/server [путь до config.json]
```

По умолчанию ищет (и создаёт, если нет) `config.json` рядом с собой.
Программа создаёт Область, случайно размещает булыжники (без коллизий по
тайлам), поднимает WebSocket-сервер и запускает игровой цикл, рассылая
номер каждого тика подключённым клиентам. Весь консольный вывод — на
английском (чтобы не зависеть от кодировки консоли).

### Протокол (WebSocket, JSON)

Сервер → клиент, сразу при подключении и после каждой регенерации:
```json
{"type": "world_snapshot", "area": {"width": 100, "height": 100}, "tick": 0,
 "paused": false,
 "terrain_seed": 54321, "terrain": { "...": "все поля из config.json/terrain" },
 "boulder_count": 40, "boulder_seed": 12345,
 "boulders": [{"x": 12, "y": 34}, ...],
 "soil": {
   "moisture": [0.42, 0.51, "...по одному float на тайл, row-major..."],
   "rockiness": [...],
   "compaction": [...]
 },
 "water": [{"x": 30, "y": 12, "depth": 1.4}, "...только тайлы с водой..."]}
```

Сервер → клиент, после каждого тика (только пока мир не на паузе):
```json
{"type": "tick", "tick": 5}
```

Сервер → все клиенты, при изменении паузы:
```json
{"type": "pause_state", "paused": true}
```

Клиент → сервер, запрос переключить паузу (в графическом клиенте — по
клавише `P`):
```json
{"type": "toggle_pause"}
```

Клиент → сервер, запрос перегенерировать мир (панель настроек, кнопка
Regenerate) — `params` имеет ту же форму, что `terrain_seed`/`terrain`/
`boulder_count`/`boulder_seed` в `world_snapshot`:
```json
{"type": "regenerate", "params": {"terrain_seed": 777, "terrain": {...},
 "boulder_count": 40, "boulder_seed": 12345}}
```
Сервер удаляет прежние Entity почвы/воды/булыжников, генерирует заново на
том же Area (размер Области регенерацией не меняется) и рассылает свежий
`world_snapshot` всем подключённым клиентам.

Пауза настоящая, а не косметическая: пока мир на паузе, `GameLoop` не
выполняет ни одной системы и не рассылает тики — это распространяется на
всех подключённых клиентов одновременно (07_TechStack.md, все
взаимодействия — через интерфейсы, единый источник истины о состоянии
паузы — на сервере).

## Десктопный клиент

Отдельный CMake-проект в `clients/desktop` — собирается независимо от
сервера (свой `add_subdirectory` на общие `third_party/` и `shared/`, см.
выше). Графическое приложение на raylib.

### Сборка

```
cd clients/desktop
mkdir build && cd build
cmake ..
cmake --build . -j
```

### Запуск

Сначала должен быть запущен сервер. Затем:

```
./client [путь до config.json]
```

По умолчанию ищет (и создаёт, если нет) `config.json` рядом с собой и
подключается к `host:port` из него.

## Структура

- `config.json` — конфигурация сервера (у клиента своя, рядом с его бинарником).
- `third_party/` — vendored-зависимости (EnTT, nlohmann/json, IXWebSocket, raylib), общие для core/server и клиента.
- `shared/` — общий код (конфигурация, путь к исполняемому файлу), общий для server и client.
- `core/` — ядро симуляции: ECS (EnTT), компоненты, системы, игровой цикл, генерация мира. Не зависит от server/clients.
- `server/` — исполняемый файл `server`, оборачивающий core: игровой цикл + WebSocket-слой (IXWebSocket + nlohmann/json).
- `clients/desktop/` — исполняемый файл `client`, графическое приложение на raylib. Получает данные только по WebSocket-протоколу сервера.
- `clients/web/` — будущий браузерный клиент.
- `docs/` — архитектурные документы проекта.
- `build.sh`/`run.sh` (Linux/macOS) и `build.bat`/`run.bat` (Windows) — сборка и запуск сервера+клиента одной командой.
